# Repository Guidelines

## Project Structure & Module Organization
- `docker-compose.yml`: defines the SITL container (`mullet_px4_sitl`) and an optional "no SITL" container for external code.
- `run.sh` / `stop.sh`: main entrypoints to start/stop the sim and attach to a tmux session inside the container.
- `config/`: runtime configuration (`drones.yaml`, `tmux.conf`, DDS QoS XML).
- `scripts/`: container entrypoint (`entrypoint.sh`) and the fleet launcher (`spawn_fleet.py`).
- `ws/`: ROS 2 workspace mounted into the container.
  - `ws/src/`: ROS 2 packages (tracked: `px4_state_machine`; gitignored deps: `px4_msgs`, `px4_ros_com`).
  - `ws/build/`, `ws/install/`, `ws/log/`: generated by `colcon` (do not commit).

## Build, Test, and Development Commands
- `cp .env.example .env`: create local env overrides (ignored by git).
- `./run.sh`: starts `px4_sitl`, creates a tmux session in `mullet_px4_sitl`, and tails `/tmp/runtime/*.log` panes.
  - Overrides: `CONFIG_PATH=config/drones.yaml`, `TMUX_CONF_PATH=config/tmux.conf`.
  - Exiting tmux ends the session and brings the compose stack down.
- `./stop.sh`: shuts down docker compose and kills the host tmux session (if present).
- ROS 2 workspace (host or inside container):
  - `cd ws && colcon build`
  - `source ws/install/setup.bash`
  - `ros2 launch px4_state_machine px4_state_machine.launch.py`

## Coding Style & Naming Conventions
- Bash: keep `set -euo pipefail`; prefer small, composable scripts.
- Python: keep runtime deps stdlib-only unless the container image is updated. `config/drones.yaml` must stay compatible with the minimal parser in `scripts/spawn_fleet.py` (avoid YAML anchors/multiline blocks).
- Config: keep `fleet[].instance` unique, starting at `0` and contiguous (`0,1,2,...`).
- ROS 2: packages live under `ws/src/<package_name>`; keep `package.xml` and `CMakeLists.txt` in sync.

## Testing Guidelines
- No automated tests are currently wired in. If you add tests, integrate them so they run via `cd ws && colcon test`.

## Commit & Pull Request Guidelines
- Commit subjects use imperative verbs and describe the change in one line (examples in history: "Add ...", "Enhance ...", "Implement ...").
- PRs include: what changed, how to reproduce (commands + relevant `config/drones.yaml` snippet), and any behavior changes (ports/topics). Do not include `.env` or `ws/build|install|log` artifacts.
