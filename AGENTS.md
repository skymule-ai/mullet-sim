# AGENTS.md (Repo Guide for Coding Agents)

This repo is a multi-vehicle PX4 SITL + Gazebo launcher (Docker) with a mounted
ROS 2 workspace in `ws/`. It also contains a Python HEDAC project under
`ws/src/hedac/` and ROS 2 packages under `ws/src/`.

## Quick Orientation
- Start/stop sim (host):
  - `./run.sh` (attaches to tmux inside `mullet_px4_sitl`; exiting tmux brings compose down)
  - `./stop.sh`
- Core launcher flow (container): `scripts/entrypoint.sh` -> `scripts/spawn_fleet.py`
- Runtime logs (container): `/tmp/runtime/px4_<instance>.log`, `/tmp/runtime/xrce_agent.log`

## Repo Layout (High-Level)
- `docker-compose.yml`: defines `px4_sitl` and `px4_no_sitl` containers (host networking).
- `config/`: runtime config (`drones.yaml`, `tmux.conf`, DDS QoS XML, etc.).
- `scripts/`: container entrypoint + fleet launcher and helper scripts.
- `ws/`: ROS 2 workspace (mounted into container)
  - `ws/src/px4_state_machine`: ROS 2 package (C++ + Python offboard node)
  - `ws/src/hedac`: HEDAC Python project + ROS 2 bridge package `hedac_ros2`
  - `ws/build/`, `ws/install/`, `ws/log/`: generated by colcon (do not commit)

## Build / Lint / Test Commands

### One-Time Setup
- Create local env overrides (ignored by git): `cp .env.example .env`
- ROS 2 deps (not tracked; clone into `ws/src/` when needed):
  - `git clone https://github.com/PX4/px4_msgs.git ws/src/px4_msgs`
  - `git clone https://github.com/PX4/px4_ros_com.git ws/src/px4_ros_com`

### Run the Simulator
- `./run.sh`
  - Reads `CONFIG_PATH` (default `config/drones.yaml`) and `TMUX_CONF_PATH` (default `config/tmux.conf`).
- `./stop.sh`

### ROS 2 Workspace (ws/)
Run these either inside the container or on host with ROS 2 sourced.
- Build all packages:
  - `cd ws && colcon build --symlink-install`
- Build a single package:
  - `cd ws && colcon build --packages-select px4_state_machine --symlink-install`
  - `cd ws && colcon build --packages-select hedac_ros2 --symlink-install`
- Run/launch:
  - `source ws/install/setup.bash`
  - `ros2 launch px4_state_machine px4_state_machine.launch.py`
  - `ros2 launch hedac_ros2 hedac_px4.launch.py`

### ROS 2 Tests (colcon)
Note: tests may not exist yet; integrate new tests so they run via colcon.
- Run all tests:
  - `cd ws && colcon test`
  - `cd ws && colcon test-result --verbose`
- Run tests for one package:
  - `cd ws && colcon test --packages-select px4_state_machine`
  - `cd ws && colcon test --packages-select hedac_ros2`
- Run a single test (common patterns):
  - CTest/gtests (regex on test name):
    - `cd ws && colcon test --packages-select <pkg> --ctest-args -R <regex>`
  - Pytest-based ament tests (pass-through pytest args when applicable):
    - `cd ws && colcon test --packages-select <pkg> --pytest-args -k "<expr>"`
  - Always follow with: `cd ws && colcon test-result --verbose`

### HEDAC Python Project (ws/src/hedac)
This is a separate uv-managed Python project (not the root `pyproject.toml`).
- Install/sync deps:
  - `cd ws/src/hedac && uv sync`
- Run standalone simulations:
  - `cd ws/src/hedac && uv run python examples/run_hedac.py --config configs/default_params.yaml`
  - `cd ws/src/hedac && uv run python examples/run_hedac.py --config configs/sitl_px4_params.yaml --no-plot`
- Lint / format:
  - `cd ws/src/hedac && uv run ruff check .`
  - `cd ws/src/hedac && uv run ruff format .`
- Tests:
  - `cd ws/src/hedac && uv run pytest`
- Run a single pytest test:
  - `cd ws/src/hedac && uv run pytest tests/test_file.py::TestClass::test_name`
  - `cd ws/src/hedac && uv run pytest -k "pattern"`

## Code Style Guidelines (Repo-Wide)

### General
- Prefer small, reviewable diffs; avoid drive-by formatting.
- Do not commit generated artifacts: `ws/build/`, `ws/install/`, `ws/log/`, `.env`.
- Keep container behavior deterministic (fail fast on config errors).

### Bash (`run.sh`, `stop.sh`, `scripts/*.sh`)
- Keep `set -euo pipefail`.
- Quote variables; treat unset vars as errors.
- Prefer readable, composable scripts over clever one-liners.

### Python: Two "Worlds"
1) Container/launcher scripts (`scripts/*.py`, especially `scripts/spawn_fleet.py`)
- Stdlib-only unless the container image is explicitly updated.
- Fail fast with actionable messages (use stderr for errors).
- Keep parsing constraints in mind (see YAML rules below).

2) HEDAC Python code (`ws/src/hedac/**`)
- Dependencies are managed in `ws/src/hedac/pyproject.toml` via `uv`.
- Use `ruff`:
  - Lint: `uv run ruff check .`
  - Format: `uv run ruff format .`

### Python Imports
- Order: standard library, third-party, local.
- No wildcard imports.
- For HEDAC internal modules, prefer explicit relative imports where already used.

### Formatting
- Python: 4 spaces; keep line length and style consistent with nearby code; use `ruff format`.
- C++: follow existing file formatting (no project-wide clang-format config present).

### Types
- Add type hints for new/changed public Python functions where practical.
- For numeric arrays, prefer `numpy.typing.NDArray` or `np.ndarray` consistent with local code.
- Avoid "stringly typed" configs: parse to `int/float/bool` at boundaries.

### Naming
- Python: `snake_case` (functions/vars), `CapWords` (classes), `UPPER_SNAKE_CASE` (constants).
- ROS 2 params/topics: keep descriptive names; do not rename without updating launch/config/docs.
- ROS 2 multi-vehicle: be explicit about `instance` and `fmu_prefix` conventions.

### Error Handling
- Prefer fail-fast validation at boundaries:
  - Config file existence, required keys, type coercion.
- Do not swallow exceptions unless you add context and re-raise or return a clear failure.
- In ROS 2 nodes:
  - Use `get_logger().info/warn/error` for operator-visible issues.
  - Avoid log spam in high-rate timers (throttle or gate with debug flags).

## Configuration Rules (Important)
- `config/drones.yaml` must stay compatible with the minimal parser in `scripts/spawn_fleet.py`:
  - Avoid YAML anchors, multi-line blocks, and advanced YAML features.
- Fleet rules:
  - `fleet[].instance` must be unique and `>= 0`
  - Launcher sorts instances ascending; lowest instance starts Gazebo server
  - Gaps are allowed but discouraged unless intentional
- Multi-vehicle ROS 2 topic prefixes:
  - instance `0`: topics at `/fmu/...` (no prefix)
  - instance `N`: topics under `/px4_N/fmu/...`
  - For multi-robot work, starting at instance `1` is recommended.
